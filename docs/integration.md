# Подключение к существующему проекту

Эта инструкция для приложения, у которого уже есть MongoDB. `playbooks/site.yml` предназначен для отдельного лабораторного стенда с собственным портом, каталогом данных и replica set. В существующем проекте подключите PBM к текущему replica set через свой Ansible-проект или другой инструмент развёртывания.

## 1. Подготовьте MongoDB и S3

- Уточните версию MongoDB, FCV и топологию. Ниже описан логический PITR для replica set. Для standalone сначала понадобится спланировать переход на replica set. Сверьте совместимость выбранной версии PBM с вашим сервером. [Матрица совместимости PBM](https://docs.percona.com/percona-backup-mongodb/latest/details/versions.html)
- Выделите бакет или отдельный префикс S3 для этого окружения. Учётной записи PBM нужны права на перечисление, чтение, запись и удаление объектов в её области хранения. Для подключения вне защищённой сети используйте HTTPS с проверкой сертификата. [Хранилища и разрешения PBM](https://docs.percona.com/percona-backup-mongodb/2.16.0/details/storage-configuration.html)
- Создайте служебного пользователя MongoDB с ролями, указанными Percona для вашей версии. Установите совместимые `pbm` и `pbm-agent` и запустите агент на каждом узле с экземпляром `mongod`, кроме арбитров. Агент подключается к своему локальному `mongod`, CLI — к replica set. Передайте каждому процессу соответствующий `PBM_MONGODB_URI` из менеджера секретов. Сохраните действующие параметры TLS и аутентификации. [Настройка доступа PBM](https://docs.percona.com/percona-backup-mongodb/2.16.0/install/configure-authentication.html) · [URI агента и CLI](https://docs.percona.com/percona-backup-mongodb/details/authentication.html)

## 2. Сделайте базовый снимок и включите PITR

Возьмите за основу [шаблон PBM](../playbooks/roles/mongo_dr/templates/pbm.yml.j2). В своей системе развёртывания подставьте endpoint, регион, бакет и префикс. Подставьте секреты из менеджера секретов при генерации файла, либо используйте поддерживаемый механизм получения S3-учётных данных из окружения. Ограничьте доступ к сгенерированному файлу. При первой настройке задайте `pitr.enabled: false` и выберите интервал `pitr.oplogSpanMin` по целевому RPO. [Настройки S3 в PBM](https://docs.percona.com/percona-backup-mongodb/2.17.0/reference/configuration-options.html)

Следующие команды выполняйте с административного хоста, где установлен CLI `pbm` и загружен URI **исходного replica set**. Если PBM уже используется, сначала проверьте его текущую конфигурацию и согласуйте смену хранилища.

```bash
pbm status
pbm config --file /secure/path/pbm-source.yml
pbm backup --type=logical --compression=s2 --wait
pbm config --set pitr.enabled=true
pbm list
```

`status` проверяет видимость агентов, `config --file` загружает конфигурацию S3, `backup --wait` ждёт окончания базового снимка. Следующая команда включает архивирование изменений. Повторите `pbm list` после первого интервала нарезки и убедитесь, что появился диапазон PITR. Закрепите `pitr.enabled: true` в управляемой конфигурации источника.

Запланируйте регулярный логический снимок и очистку средствами PBM. Пример расписания есть в [роли Ansible](../playbooks/roles/mongo_dr/tasks/schedule.yml). Следите за возрастом доступной точки, свободным местом и локальным окном oplog. Если это окно истечёт во время сбоя выгрузки, понадобится новый базовый снимок.

## 3. Проверьте восстановление на отдельном экземпляре

Подготовьте чистый совместимый replica set для DR. Для простого сценария используйте то же имя replica set. Установите агент PBM и подготовьте `pbm-recovery.yml` с тем же бакетом и префиксом и с `pitr.enabled: false`. Перед запуском проверьте, что `PBM_MONGODB_URI` указывает **на DR**, и отключите подключения приложения к этой базе.

```bash
pbm config --file /secure/path/pbm-recovery.yml
pbm list
```

Первая команда записывает конфигурацию и при смене хранилища запускает импорт каталога. Дождитесь окончания импорта и повторите `pbm list`. Если каталог нужно обновить вручную, выполните `pbm config --force-resync --wait`. После этого выберите нужный момент из доступного диапазона, укажите имя своей базы и запустите на DR:

```bash
APP_DB=myapp
TARGET_UTC=2026-11-16T21:04:50  # Пример. Подставьте время из своего каталога.
pbm restore --ns "${APP_DB}.*" --time "$TARGET_UTC" --wait --yes
pbm list --restore
```

`--ns` ограничивает восстановление указанной базой, `--time` задаёт время в UTC, а `--yes` подтверждает перезапись соответствующих данных на DR. Последняя команда показывает статус. При другом имени replica set сверяйтесь с инструкцией по remapping. [Селективный PITR](https://docs.percona.com/percona-backup-mongodb/latest/usage/pitr-selective.html) · [Сопоставление replica set](https://docs.percona.com/percona-backup-mongodb/latest/features/restore-remapping.html)

Сравните количество документов, индексы и прикладные инварианты. Воспроизведите пользователей и права из конфигурации проекта. Если приложение использует транзакции между несколькими базами, согласуйте объём восстановления и отдельно проверьте общие инварианты. Зафиксируйте возраст последней доступной точки, время восстановления и проверки, затем проверьте переключение клиента во время DR-учения.

На стенде подтверждён селективный PITR одной базы с выключенным источником. Совместимость с топологией, правами и данными вашего проекта проверяется отдельным прогоном перед внедрением.

## Что может усложнить внедрение

| Сложность | Как проверить и что сделать |
|---|---|
| Версия MongoDB, FCV или топология отличаются от стенда | Проверьте матрицу совместимости и наличие агента на каждом нужном узле через `pbm status`. Для standalone запланируйте переход на replica set. Для шардинга проверьте отдельные требования к установке и восстановлению. |
| PBM видит MongoDB, но не может писать в S3 или импортировать каталог | Проверьте сеть, TLS и права на бакет именно под учётной записью агента. Прогоните полный цикл `pbm backup` → `pbm list` → импорт каталога на DR. Доступ на чтение может оказаться недостаточным для обновления служебных объектов PBM. |
| При сбое S3 локальный oplog переполняется раньше, чем возобновляется выгрузка | Измерьте скорость заполнения oplog на пике и проверьте запас времени. Следите за возрастом последней доступной точки через `pbm list`. При разрыве цепочки нужен новый базовый снимок. |
| Полный снимок или восстановление не укладываются в допустимое окно | На объёме и нагрузке своего проекта измерьте задержку запросов во время горячего бэкапа, а на DR отдельно замерьте чтение из S3, загрузку данных, индексы, replay и проверку. Лабораторные показатели зависят от данных и инфраструктуры. |
| Документы восстановились, но приложение не готово к переключению | Проверьте пользователей, роли и прикладные инварианты. Для транзакций между базами проверьте согласованность на нужном наборе баз. Проведите учение с отключённым источником и тестовой сменой строки подключения. |
| Отказал сам бакет или потерян доступ к его ключам | Проверьте восстановление из независимой копии архива и доступ к её учётным данным. Один S3-шлюз на одной ВМ покрывает потерю исходной ВМ, а потеря шлюза требует отдельного плана. |
