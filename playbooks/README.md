# Ansible: настройка стенда и проверка восстановления

Ansible автоматизирует установку компонентов, создание резервных копий, запуск эксперимента и восстановление на выбранном получателе. Playbook задают хосты и порядок операций; роли содержат повторно используемые задачи для отдельных компонентов.

## Требования

- На контроллере: Ansible Core 2.19+, OpenSSL и SSH-доступ к управляемым ВМ.
- На ВМ лаборатории: Ubuntu 24.04 amd64, Python 3, systemd и права root через SSH или sudo.
- Сеть между ВМ и доступ к S3 подготовлены заранее. Сеть и мониторинг эти playbook не устанавливают.

Внешние коллекции Ansible не требуются: используются модули `ansible.builtin`. Системные пакеты перечислены в документации каждой роли.

Все команды ниже выполняются **на Ansible-контроллере из корня проекта**, где находится `ansible.cfg`. Удалённо Ansible запускает задачи на хостах из inventory.

## Роли

| Роль | Назначение | Документация |
|---|---|---|
| `mongodb` | Установка отдельного экземпляра MongoDB и инициализация одноузлового replica set | [Требования, переменные и пример](roles/mongodb/README.md) |
| `s3_storage` | Установка лабораторного Versity S3 Gateway, создание пользователя и бакета | [Требования, переменные и пример](roles/s3_storage/README.md) |
| `pbm` | Настройка PBM, PITR, расписания, ротации, локальных метрик и отдельных операций backup/restore | [Требования, переменные и примеры](roles/pbm/README.md) |

Все роли находятся в `playbooks/roles/`; этот путь задан в `ansible.cfg`. Роль `pbm` можно использовать отдельно с уже существующими MongoDB и S3. [Подключение к своему проекту](../docs/integration.md).

## Inventory и переменные

| Файл или каталог | Что задаётся |
|---|---|
| `inventory/hosts.yml` | Рабочие SSH-адреса и группы `mongodb`, `storage`, `pbm_agents`; создаётся из `hosts.example.yml` |
| `inventory/group_vars/all/main.yml` | Источник эксперимента, получатель и архив для регулярного учения |
| `inventory/group_vars/all/s3.yml` | Справочник архивов `backup_archives` и параметры лабораторного gateway |
| `inventory/group_vars/all/secrets.yml` | Локальные пароли и ключи; файл исключён из Git |
| `inventory/group_vars/mongodb.yml` | Общие настройки лабораторных MongoDB |
| `inventory/group_vars/pbm_agents.yml` | Передача настроек MongoDB и выбранного архива в переменные роли PBM |
| `inventory/host_vars/` | Флаги PITR и расписания конкретного хоста |

Значения в `roles/*/defaults/main.yml` — исходные настройки ролей. Inventory переопределяет их для лаборатории: например, роль MongoDB использует порт `27017`, а стенд — `27117`. Параметры `-e` переопределяют значения для конкретного запуска: `-e experiment_docs=4096` задаёт число начальных документов.

Имена `mongo-01` и `mongo-02` — имена хостов в inventory. Роль MongoDB для них одинакова; назначение узлов задают playbook и переменные PBM.

## Подготовка и запуск

```bash
# Создать рабочий inventory, сохранив существующий файл, если он уже есть.
cp -n inventory/hosts.example.yml inventory/hosts.yml
# Сгенерировать недостающие секреты; существующие значения сохраняются.
bash scripts/init-secrets.sh
```

До следующих команд укажите SSH-адреса в `inventory/hosts.yml` и доступные адреса S3 в `inventory/group_vars/all/s3.yml`. Проверьте настройки MongoDB и флаги в `host_vars/`.

```bash
# Проверить SSH-подключение и возможность выполнения Python-модулей на всех ВМ.
ansible all -m ping
# Настроить S3 на storage, MongoDB на mongodb и PBM на pbm_agents.
ansible-playbook playbooks/setup.yml
```

Если sudo требует пароль, добавьте `--ask-become-pass` к `ansible-playbook`. При зашифрованном Ansible Vault файле секретов добавьте `--ask-vault-pass`. Это два разных пароля: первый нужен для повышения прав на ВМ, второй — для расшифровки переменных на контроллере.

## Playbook и место выполнения

| Playbook | Где выполняется | Что делает |
|---|---|---|
| `setup.yml` | Группы `storage`, `mongodb`, `pbm_agents` | Настраивает компоненты; первая полная копия и восстановление отдельными задачами здесь не запускаются, но включённые таймеры затем работают по расписанию |
| `backup.yml` | Один хост `backup_target` из `pbm_agents` | Создаёт полную логическую копию в S3 и выполняет ротацию |
| `experiment.yml` | Хост `experiment_host` | Создаёт данные, полную копию, окна изменений и отчёт `artifacts/experiment.json` |
| `restore.yml` | Хост `restore_target`; отчёт на контроллере | Импортирует каталог, выполняет PITR и запрошенную проверку данных; сохраняет результат и метрики, включая ошибки |
| `drill.yml` | Источник и получатель из `experiment_host` и `drill_target` | Запускает небольшой эксперимент, готовит пустой получатель, восстанавливает данные и проверяет результат |
| `scaling-setup.yml` | Два хоста с явно заданным `scaling_instance: true` | Подготавливает отдельные экземпляры на порту `27217` из уже установленных пакетов для серии 1–5 ГиБ |

Команды для подготовленной лаборатории:

```bash
# На mongo-01 создать полный логический бэкап и применить срок хранения.
ansible-playbook playbooks/backup.yml -e backup_target=mongo-01
# На источнике создать небольшой контрольный набор и измерить архивирование изменений.
ansible-playbook playbooks/experiment.yml -e experiment_docs=4096
# На mongo-02 восстановить последнюю контрольную точку эксперимента из архива lab.
ansible-playbook playbooks/restore.yml \
  -e restore_target=mongo-02 -e restore_confirm=mongo-02 \
  -e restore_archive=lab -e restore_manifest=artifacts/experiment.json
# Выполнить всё учение; получатель должен быть выделен только для тестового восстановления.
ansible-playbook playbooks/drill.yml
```

`restore_confirm` подтверждает конкретный хост назначения. Восстановление перезаписывает выбранные данные на нём. `drill.yml` дополнительно заменяет рабочий каталог данных получателя пустым, сохраняет предыдущий каталог и после успеха оставляет один предыдущий каталог автоматических учений. Используйте выделенную DR-ВМ.

Для импорта только каталога передайте `restore_list_only=true` вместе с получателем, подтверждением и архивом. Для уже существующих MongoDB/S3 используйте независимую роль `pbm` по инструкции интеграции. Флаги `prepare_mongodb=false` и `prepare_storage=false` у `setup.yml` пропускают соответствующие роли, но требуют самостоятельно подготовленных компонентов.

### Отчёт каждого восстановления

Команда `restore.yml` остаётся прежней. После начала операции на контроллере создаются `artifacts/restore.json` и `artifacts/restore.prom`; путь можно изменить параметром `restore_report_path`. В JSON находятся получатель, база, целевое время, длительность и этап ошибки. `restore_success` — результат PBM, `verification_status` — отдельный результат проверки данных, `success` — итог всей операции.

При подключении `.prom` к Node Exporter и правил Prometheus ошибка ручного восстановления тоже вызывает Telegram-уведомление. Отчёты `drill.json` и `drill.prom` принадлежат полному учению и одиночным восстановлением не обновляются. [Настройка уведомлений](../docs/monitoring.md#уведомления-в-telegram).

`--check` и просмотр каталога не записывают успешное восстановление. Ошибки аргументов до начала операции прерывают запуск без нового отчёта. При прерывании Ansible или потере SSH начальный отчёт может остаться с `running: true`; для такого случая есть правило `RestoreStuck`.

Для сравнения размеров запускайте `experiment.yml` и `restore.yml` напрямую по [инструкции](../examples/scaling/README.md). Параметр `experiment_target_gib` задаёт объём данных. Скрипт `scripts/plot-scaling.py` строит графики по сохранённой сводке измерений. Очистка источника разрешена только для `dr_benchmark` в replica set `drbench`.

## Подготовка пустого получателя

У `playbooks/restore.yml` есть дополнительный параметр `-e restore_reinitialize=true`. Он сохраняет прежний каталог `data` в отдельном каталоге и подготавливает пустую MongoDB перед восстановлением. Параметр по умолчанию выключен и доступен только для экземпляра с маркером роли `mongodb`. Используйте его на выделенном лабораторном получателе; обычная установка роли MongoDB данные не сбрасывает.

Получатель должен иметь PBM с выключенными PITR и расписанием копий. Перед изменением данных роль проверяет подтверждение хоста и фактическое состояние PITR, затем выбирает архив и выполняет `pbm config --force-resync --wait` и `pbm restore --time … --ns … --wait --yes`. Временная занятость автоимпортом каталога обрабатывается ограниченным повтором; прочие ошибки возвращаются сразу.

```bash
# Проверить синтаксис playbook без подключения к ВМ и выполнения задач.
ansible-playbook -i inventory/hosts.example.yml playbooks/setup.yml --syntax-check
# Проверить обработку ошибок и ограничения восстановления на локальной имитации PBM.
python3 -m unittest discover -s tests -v
```
